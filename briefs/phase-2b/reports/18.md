## Design decisions

**Crawl** (`bun tools/crawl.mjs --id a,b | --queue [--limit n] | --pilot [--force] [--report]`)
- Sources go cheapest first: corpus llms.txt / README / SKILL.md / sitemap.json, plus what the catalog knows
  (`known`: item counts by kind, top item elements, 15 sample item names, registry / llms / skill / mcp flags,
  sitemap size, the parent site for pages). Then plain HTTP through `createFetcher` (2 req/s per host, robots.txt;
  a host is stopped after 3× 403/429), with the Scrapling backend for enabled hosts. Repos: corpus README / SKILL.md,
  else `raw.githubusercontent.com/<o>/<r>/HEAD/README.md` (its robots.txt is a 404).
- Hosts that `scrapling-hosts.json` disables are never requested. This also covers their subdomains
  (`shop.ui8.net`) and a redirect that lands on one (dropped unread).
- One digest per entry: `hints` (source hints), `hints_hash`, `known`, `status` ok | partial | blocked with a
  `reason`, `pages[]` (url, final_url, status, title, meta / og description, og:image, h1–h3, nav texts, visible
  text, internal links as paths), `skipped[]`, and `tokens`. It is written as 1-space JSON, exactly what `tokens`
  measures.
- Boilerplate removed: script / style / svg / `<pre>` code / nav / footer / cookie-consent blocks, cookie and chrome
  lines (skip-to-content, Webflow form messages …), lines repeated within a page, lines and nav texts repeated
  across pages.
- Budgets:
  - per page: ≤ 12k chars;
  - per site: 14k chars total (llms.txt 4k · homepage 5.5k · extra pages 3k each);
  - per repo: 16k;
  - per page entry: 5k.
- Extra pages: one per bucket (docs, components, pricing, about, license, matched on the first path segment), then
  shallow docs / components pages. Index pages win over deep ones, because depth costs more than a good source
  (llms > nav > home > sitemap) earns. Never blog, login, legal, locale, query or asset urls. A walled homepage
  stops the crawl unless an llms.txt exists.
- Statuses:
  - **blocked**: robots, 401/403/429/503 or a challenge, an HTTP 202 challenge, a login redirect, a JS-only shell,
    an empty page, a disabled host;
  - **partial**: a JS-app page with only title + meta readable (< 40 words plus app markers), or a walled homepage
    with corpus text.
- Dead = `reach.reason` dead / repo-gone: skipped and listed. `no-endpoint`, `bot-walled` and `gated` are crawled.
  Two of the pilot's "hard" entries read fine: codepen-io (bot-walled in reach) and the walled medium.com article.

**Schema, prompt, check**
- Taxonomy ids are not enums in the schema. The check validates them against `taxonomy.json`, so the schema can't
  drift from it. Also checked: a variant's element must be in `elements`, `related.parent` must be a catalog id, and
  id / kind / url must match the entry.
- Keyword normalization: NFKC, lowercase, single spaces, last word singular (with exceptions: menus → menu; glass,
  canvas, analytics, docs, nextjs stay). Then spelling variants map through the taxonomy ("nav bar" / "nav-bar" /
  "navbars" → navbar, "megamenu" → "mega menu"), Turkish words become English ("animasyon" → animation), and
  duplicates go.
  - **Different wordings are deliberately not merged**: "tool call" is not turned into "ai agent ui", because search
    would lose the words.
  - Stack spellings are normalized too ("Tailwind CSS" → tailwind). `keywords_manual` is never touched.
- `metadata-check --id a,b` (what a session runs) does not write `_review.md`, so parallel sessions never write the
  same file. The full check writes it.
- Review rules: confidence < 0.6, or a primary category outside the "hint categories". Those are the source
  categories plus text-derived ones, without the default `dev-ai-tools` bucket: a default is the absence of a hint.

**Queue / batches**
- `hints_hash` = sha256 of the source hints (url, kind, name, desc, title, about, labels, note, categories after
  overrides; no mentions), from `loadItems({ metadata: false })`. Merged catalog values never feed it, so a merged
  record does not re-queue itself.
- `_queue.json` order: curated → readable → rest; it holds a token estimate. Run on main data it shows 2,633 queued,
  3 current, 43 dead.
- `metadata-batch` writes `_batches/<n>.md` (the full prompt, the ids, the steps, marker
  `METADATA-BATCH-<n>-DONE`) and `<n>.ids`. A watcher can run `metadata-check --id "$(cat <n>.ids)"`, which is more
  reliable than grepping the marker in a pane that may echo the file. Only entries with a digest are batched.

**Build merge**
- Order: sources → categorize → overrides → hint fallback → records → overrides again.
- In the second override pass, hand fixes beat metadata, including `type`.
- A record is normalized and validated before merging; an invalid one is skipped and named.
- Fields: metadata wins only for the fields it states, so a page's light record keeps the source categories.
  Empty, `unknown` and null values are dropped from catalog.json. `evidence`, `extractor`, `schema_version`,
  `extracted_at` and `hints_hash` never reach it.
- Status: `metadata` is `missing` without a record, else the record's status. A blocked or dead record keeps the
  source values.

**Hint fallback** (measured, `tools/metadata.mjs` `hintElements`)
- `strong` = the old index-time rule (name + desc), moved to the build.
- `weak` = each label, plus `about` and notes ≤ 100 chars, only for entries filed under a UI category, minus
  elements that are noise in prose (team, features, ai-agent-ui, cursor, map, list, select, 404, …).
- Not used:
  - **long notes**: X post text, mostly noise (job ads, tool lists);
  - **the source category label**: "Bölüm galerileri (navbar / hero / footer / CTA)" would tag 31 galleries with
    all four elements.
- catalog.json carries `elements` + `elements_from: "hints"` + `elements_weak`.
- Weak elements only filter and show; they are not ranked. Indexed even at the about field's weight, they moved two
  eval queries down (gridddy for "cta inspiration", icoon-co for "3d icons"; MRR 0.720 → 0.709). Both hits are real
  but not in the expected lists.
- Coverage: **642 → 729 entries** with elements (87 newly tagged, 104 gaining weak elements, 869 tags).

**Search**
- New `keywords` field, weight 3: the record's keywords + stack + formats + a free / freemium pricing word.
- Entries with a record index:
  - summary in `description` and its description in `about`;
  - `contains` in its own field at about's weight;
  - type label in `category`, variants in `variant`;
  - and no longer their X labels.
- **One deviation from the brief's wording**: `contains`, `keywords` and the record description do not count towards
  a record entry's BM25 length (item descriptions already had the same rule). Counted, a record made its own entry
  rank lower: navbar-gallery fell from 17.7 to 14.3 on "navbar" and dropped out of the `search_resources` answer, and
  magicui went from 35.7 to 30.0 on "magic ui components".
- Entries without a record index exactly as before (tested: identical postings).

**get_resource**
- With a record: type, about (clipped), contains, elements + kinds, top 12 keywords, formats / stack / pricing /
  license, related (a related url that is a catalog entry names its id). No "people call it". Empty and unknown
  fields are omitted. It shrinks in 4 steps to stay ≤ 2,000 bytes.
- Without a record, the text is unchanged (byte-identical to main for the 3 entries before their records).
- `Resource` schema gains `metadata, type, elements, contains, keywords, formats, stack, pricing, license, related`.
  `elements_from` was dropped to keep the output schemas under their 13 KB test budget.

## Token estimate for the full run

- **Unique tokens: ≈ 8.2M**, against the plan's 21M. Based on the 2,633 queued entries and the pilot means
  (sites 2,988 incl. blocked, repos 1,717, pages 1,769):
  - digests: 1,179 × 2,988 + 568 × 1,717 + 886 × 1,769 ≈ 6.1M;
  - prompt: one per 20-entry batch, 132 × ~3.9k ≈ 0.5M;
  - output: 2,633 × ~600 ≈ 1.6M.
- `metadata-queue` prints 16.3M today, because it uses the plan's averages for the 2,585 entries without a digest.
  It switches to measured sizes as the crawl runs.
- **Caveat — the agent loop.** An omp session re-sends its whole context on every turn: about 3 turns per entry
  (read, write, check), and the context grows by about 3k tokens per entry. Assuming ~12k of fixed context (batch
  prompt + omp's own system prompt, a guess), billed input is roughly:

  | batch size | billed input per entry | whole run |
  | --- | --- | --- |
  | 20 | ~125k | ~330M |
  | 10 | ~80k | ~200M |

  Most of it is a cached prefix on DeepSeek. Reasoning output at `--thinking max` comes on top. RUN.md recommends
  `--size 10` for the pilot, and the pilot should replace these guesses with omp's real usage.

## Unsure / for the owner

- **Prompt rule removed.** The first draft forbade keywords that repeat the type or categories. I removed the rule:
  it would drop exactly the phrases people search with ("agent skill").
- **Record type and the asset gate.** `tag.mjs`'s asset gate (icon-set / asset-library get no item elements) still
  reads only `overrides.json`. Wiring record types into it would change item tags after the run. I left it for after
  the pilot review, because a mis-typed record would silently untag a whole registry.
- **Smoke records in the pilot.** `--pilot` includes the 3 smoke entries. Running the pilot's batches overwrites my
  records with DeepSeek's (useful for comparing; keep a copy if you want mine).
- **Freefaces robots.** freefaces-gallery's robots.txt disallows `/` for `*`, so it stays blocked by design.
- **`thinking max` cost.** Reasoning tokens at `--thinking max` are not in any estimate here; the pilot should
  measure them.
- **Partial-run ranking.** In a partly-run catalog, record entries carry many more matching words than entries
  without one (see "dark mode landing page gallery"). This is expected to fade as coverage grows; worth re-checking
  the eval after the pilot.
