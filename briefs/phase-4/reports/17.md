## Schemas (`tools/schemas.mjs`)

- `Matched`: which query word hit which field (`{word, field}`).
- `KindCounts`: the focus element's kinds with counts (`{kind, count}`), most common first.
- `ResourceHit`: a site, page or repo hit (`id, name, url, kind, summary, flags, pages, matched`).
- `ComponentHit`: a component, gallery example or docs page hit (`id, name, registry, host, access, granularity, type, url, elements, kinds, stacks, also, matched`).
- `PageHit`: one list_pages line, either a mapped page (`name, url`, an `id` for code items) or a raw sitemap url.
- `Resource`: get_resource for an entry (categories, capabilities, reachability, registry, llms urls, local copy, mapped counts).
- `Component`: get_resource for a component id (tags, url, stacks, examples, install url and command).
- `ComponentSource`: get_component (`status` ok|page|gated|no-registry|unavailable, type, the three dependency lists, install url and command, page url, files with sizes, `chars`, `offset`, `next_offset`, and the examples shown or left out).
- `ContentAnswer`: get_content (`mode` whole|outline|query|section|none, source, size, section hits, `next_offset`, `truncated`).
- `InstallPlan`: get_install_command (`command`, urls, items, dependency lists, `skipped` with a reason and the closest ids).

There is one `outputSchema` per tool: search_resources, search_components, list_pages, get_resource
(`{resource, component}`, one of them null), list_components, get_content, get_component, get_install_command.

## Design decisions

1. **Third-party bodies stay out of `structuredContent`.** Docs text and component source appear only in the text,
   inside `<untrusted-content>`. `structuredContent` describes them by size and position: files with char counts,
   `offset`, `next_offset`, section numbers. This keeps the prompt-injection boundary for clients that hand
   `structuredContent` to the model, and it means no body is sent twice.
2. **Stable fields.** Every property is `required`, with `null` or `[]` when the value is unknown, so a consumer never
   has to check whether a key exists. I did not use `additionalProperties: false`: a client SDK that validates
   strictly would reject a whole answer over one extra key. Instead, the test validator is strict and flags any field
   the schema does not declare.
3. **Protocol gating.** A session that negotiated `2025-06-18` gets `outputSchema` in tools/list, plus `structuredContent`
   and `resource_link` items on every successful call. A `2025-03-26` or `2024-11-05` session gets exactly the old shape:
   one text item, no extra fields. A test checks that the text is byte-identical across the two versions.
   Errors stay `isError: true` text with no `structuredContent`. Soft answers ("has no shadcn registry", "needs a licence",
   "is a docs page") were successes before and still are; their state is now in `status` or `note`.
4. **`resource_link` only for primary urls.** get_resource links the entry url (for a component, its page url, else its
   registry JSON). get_component links the registry JSON url when it is known, else the page. get_install_command links
   each included item's JSON url, since those urls are the answer. Search hits get no links.
5. **tools/list budget, split in two.** The model-visible part (names, descriptions, input schemas, annotations) stays
   **≤ 8 KB**: it is 7,940 B for 8 tools, against 7,429 B for 7 tools before. To fit the 8th tool, I tightened
   existing descriptions; no capability is dropped. The output schemas add 12.2 KB on 2025-06-18. To my knowledge,
   clients validate against them and do not put them in the model's context, so they get their own budget
   (≤ 13 KB, tested). `$defs`/`$ref` share ComponentHit and ResourceHit inside search_resources, which brought the
   schemas down from 14.6 KB to 12.2 KB.
6. **get_install_command.** Each item resolves to its registry JSON url in this order: `install_url`'s layout (the
   probe's `item_status: 200` base), then the corpus definition (`items/<name>.json`, else the `registry.json` entry,
   which also carries the dependencies). That needs no network. Only when the corpus lacks the definition does it fetch
   live, then fall back to `resolveItemBase`. Urls are deduplicated into one command across registries, and the text
   groups items by registry. An id defaults to the ts-tw build of a stack-merged component; `{ref, name}` can name any
   build. Unknown ids get the 3 closest code items, ranked within the same registry first. The 25-item cap is enforced
   by `maxItems` in the input schema.
7. **get_component.** By default it returns one 20k window, and `max_chars` goes up to 40k. When there is more, the
   answer gives `next_offset` and says how to get it: `more: offset=N (M chars left) — get_component(...)`. The whole
   answer, examples included, never exceeds 40,000 chars: the window shrinks to fit the header, and examples share
   whatever room is left. Examples that do not fit are listed by name. Before going live, the corpus
   `items/<name>.json` is now also used as a local source. Local copies now state their type and dependencies too.
8. **follow_url.** The rules live in `lib.mjs` as pure functions. A url is fetched only if it is https on port 443,
   has no credentials, and has a public host name (no IP literal, localhost, `.local`/`.internal`, single-label or
   numeric host). It must also be on the entry's own site (`www.` or not) or listed in its llms.txt. At fetch time the
   server also checks every resolved address against private, loopback, link-local, CGNAT and multicast ranges.
   Redirects are followed manually: up to 5 hops, each re-checked by the same rule, with the 3xx body drained. Bodies
   are capped at 2 MB, and one 15 s timeout covers the whole call. An HTML page is turned into text with markdown
   headings, so the outline, query and section modes find its sections. The answer goes through the existing
   `contentAnswer`, wrapped in `untrusted(...)`.
9. **list_components.** `query` keeps a component only if every query word appears in its name, title or description.
   `type` accepts `ui` as well as `registry:ui`. `offset`/`limit` page the list (default 60, ≤ 300) with `next_offset`
   and a `→ more: offset=N` line. Each line keeps its page url.

  - refused: another origin not listed, http, `file:`, IP literals (`127.0.0.1`, `[::1]`, `10.x`, `169.254.169.254`,
    `2130706433`, `0x7f.1`), localhost, `*.localhost`, single-label, `.local`, `.internal`, a non-443 port, credentials;
  - redirect hops checked by the same rule (on-site and listed allowed; off-site, http and IP refused);
  - private and public addresses classified.
- The server refuses a bad `follow_url` before any fetch, and `file` + `follow_url` together.

## Things I was unsure about

- **Is `outputSchema` model-visible?** I assumed clients use it for validation and do not show it to the model, which
  is why the 8 KB budget covers only the visible part. If some client does put it in the model's context, it costs
  about 12 KB more per session.
- **"One runnable command per package manager form".** I read this as one command, in the form of the requested
  `package_manager`, not all four forms at once.
- **resource_link for get_install_command.** It gets one link per included item JSON url, not a single link.
- **DNS rebinding.** The resolved-address check runs before `fetch`, which resolves again on its own (time-of-check
  vs time-of-use). Closing that fully needs a pinned-IP connection, which `fetch` cannot do without dependencies.
  The allow-list (the entry's own site or a url its llms.txt lists) keeps the reachable set small.
- **A flaky live host.** `follow_url` on `https://www.magicui.design/docs` (a 308 to `/docs`, 684 KB of HTML) passed
  2 of 3 runs. In the third, Bun's fetch stalled mid-body, the 15 s cap fired, and the tool returned a clean
  `isError`. curl always took ~0.5 s. It looks like the host or Bun's HTTP client, not the tool. The 3xx body is now
  drained in any case.
- **HTML to text is deliberately crude.** It drops script, style and head, makes h1–h6 into `#` headings and li into
  `- `, then strips tags. That is enough for the section modes, not a readability extractor.
- **Description trims.** To keep tools/list under 8 KB I shortened existing tool and parameter descriptions. For
  example, search_resources no longer repeats the `unreadable:<reason>` note, since INSTRUCTIONS already says it.
  Please check you are fine with the wording.
