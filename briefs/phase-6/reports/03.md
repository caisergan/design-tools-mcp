## The crash, and the fix

The first run died at 15:02 after 1,400 pages with an **uncaught `TimeoutError`**. Cause: `AbortSignal.timeout(30s)`
also aborts the response **body**, so `readMetaHtml`'s `reader.read()` threw while my `try/catch` only covered
`fetch(url)` — the throw escaped `fetchComponent`, the loop and the process. Fix, all in `tools/api-21st.mjs`:

- `fetchPage()` now wraps the single round trip (request **and** body read) and returns
  `{ status: 0, error: "timeout" | message }` instead of throwing; `getText()` does the same for tag pages.
- `fetchComponent()` retries `0/429/5xx` three times (`Retry-After`, else 2 s / 4 s), and returns
  `{ status: 429, abandon: true }` when the server asks for > 60 s.
- The run loop has a per-page `try/catch` (one page can never end the run again), records the `error` field on
  status 0, and counts status 0 toward the 10-consecutive-failure stop.
- A status-0 record (no HTTP answer) is retried on resume, unlike a 404; `--refresh` still refetches everything.
- Tests: a rejecting request, a `ReadableStream` that errors after one chunk (the exact crash), 503 → 200 with
  `Retry-After: 1`, `Retry-After: 600` → abandon, and 404 not retried.

## Open problems

1. **Category pagination is client-side.** Only page 1 of a tag page is server-rendered (166 unique
   `/@author/components/name` links for `s/hero`; 200 hrefs, some listed twice); `?page=2` returns the *identical*
   page and later pages load from an endpoint under `/api/`, which robots.txt disallows. So membership is partial:
   251 tags × page 1 = 5,849 components of 7,394. Deeper pages are unobtainable without touching `/api/`.
2. **396 of 647 tag pages were not fetched** because their slug maps to no taxonomy element (`2d`, `animated`,
   `framer-motion`, `block`, …): such membership could not tag any item. If the coordinator later wants these tags
   for other purposes, drop the filter in `fetchCategories` (one line) and re-run `--categories`; it is resumable.
3. **Resume rule for status 0** deviates slightly from the brief's "keep failed ones … so the run doesn't retry
   them": only status 0 (timeout/connection, never a settled answer) is retried on resume; every HTTP status,
   including 404, is kept and skipped. The final file contains no status-0 records.
4. **The 7 soft-404 pages** stay in `components.json` with status 404 and yield no items. If they should be dropped
   from the store, they are the only entries with `status !== 200`.
5. **`apiItems` is not wired into `tools/items.mjs`** (as the brief requires). For the coordinator: call it where
   adapters 1–2 run in `buildItems` (`apiItems(domain, parent, { overrides, taken })`; returns `[]` for other
   domains; skips ids in `taken`), then re-run `bun tools/index.mjs`. Expect ~7.4k new items — brief 06 checks the
   < 25 MB index limit.
6. Two research probes were made before the crawl and are not part of the numbers: 8 hand-picked component pages
   (2 of them valid) and the two `s/hero` requests used to test pagination.
