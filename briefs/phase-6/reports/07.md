# Brief 07 report — `get_content` returns matching sections, not the first 80 KB

Branch `phase6/get-content` (worktree). Everything below was measured on this branch on 2026-10-07 with
`bun` (Bun 1.4.0), on the private `catalog/` copies in this worktree (schema 3, `catalog/search-index.json`
present) and the shared corpus symlink. No network call in any test or measurement.

`get_content` now answers one of four ways: `section=<n>` → that section; `query=…` → the 4 best-matching
sections (~2.5 KB each, paged with `offset`); a body ≤ 12 KB → whole (unchanged); a bigger body → an
**outline** with section numbers. Splitting and BM25 section ranking are pure functions in the new
`tools/sections.mjs`; the server caches the split + term stats for the last 20 documents.

## How the brief's rules were read

- **Page separators.** `---` opens a page when the next non-blank line is a heading **or** a
  `Source:`/`URL:` line **and** the page it opens contains a heading. That last clause is the one
  interpretation this report flags: `sunglasses.dev`'s 112 `---`/`URL:` blocks contain no heading at all,
  so by the rule above they are metadata lines, not sections — the brief's own rule 3 names
  `sunglasses.dev` as the "no headings" case, and this is the only reading that satisfies both sentences.
  Page headings reset the trail (`---` + `## Kitchensink App` → path `Kitchensink App`, not the previous
  page's child).
- **Chunking** applies to any heading-free span > 200,000 chars, which is what makes sunglasses.dev
  (2.27 M chars under a two-line title block) and magicui.design (661 KB, zero headings) come out as
  3 KB chunks; a chunk keeps the `URL:`/`Source:` line above it, so its answer still names its page.
  Structured docs (largest heading gap 47 KB in the corpus's big files; 15 KB–186 KB range measured) are
  never chunked.
- **Outline collapse**: levels ≤3, then ≤2 (the brief's "top two levels"), then ≤1, then truncation —
  the first fit wins, and when it collapses or truncates the answer says how many sections it left out.
- **`query` budget**: sections are capped at 2,500 chars each and the returned body at 8,000 bytes, so a
  4-section answer spends its budget on four sections (~1,850 chars each) instead of three full ones.
- **Instruction line**: the brief says "line 4 of the server instructions"; the `get_content` clause is
  item 5 in the `INSTRUCTIONS` array (index 5, 6th element) — that is the line edited.

## Open problems

1. **`sunglasses.dev` page sections** — see "How the brief's rules were read". If the coordinator wants
   the literal rule 2 (`---` + `URL:` opens a page even without a heading), the change is one condition in
   `splitSections` and sunglasses.dev would answer with 112 page sections (≤12 KB each, each with its page
   URL) instead of 781 chunks. Both readings pass every test in the brief.
2. **Chunk titles in flat dumps** are the brief's rule (first non-empty line), so sunglasses.dev's outline
   shows body fragments (`§8 "what does this package do?". And if the README is poisoned…`) rather than
   page titles. The `URL:`/`TITLE:` lines would give nicer titles; the chunk's *source* does carry the page
   URL (780 of 781 chunks).
3. **Stemming is search.mjs's** (`installation` → `installat`), so a query matches only that exact form;
   `install`/`installing` are a different stem. Deliberate: `query` must rank like `search_resources`
   does, and the brief allows no new dependency. `get_content`'s "no section matches" line lists the
   section-title hints so the agent can re-word.
4. **Section cache memory** is unbounded per document (stats ≈ a few MB for a 2.5 MB doc, capped at 20
   documents ≈ tens of MB); nothing evicts on memory pressure beyond that FIFO cap of 20.
5. `offset` is documented as paging the *ranked sections* (the brief's `more: offset=4`), not characters.
